# Idea Refining：想法收敛技能

[English README](README.md)

Idea Refining 是一个主要面向 Codex 的纯指令型智能体技能。它会在宿主智能体回答或执行之前，将宽泛、模糊、依赖偏好的请求收拢成最小充分规格。

它的核心是划定边界，而不是进行穷尽式询问。每个问题都必须能够改变范围、内容、实现路线、可靠性、质量或验收标准等下游决策。重复、可推断、时机过早和低影响的问题应被删除。

v1.1 重点减少不必要的追问，强化及时停止，消除无信息的二次批准，并在交接时精确保留用户提供的源信息。

## 快速开始

1. 将完整的 `idea-refining` 文件夹复制到项目级或用户级 Codex 技能目录。
2. 在对应项目中启动或重启 Codex。
3. 使用宽泛请求显式调用技能：

~~~text
$idea-refining 帮我定义一个用于点评学校及周边餐饮的网站。
~~~

`agents/openai.yaml` 已启用隐式调用，因此符合适用范围的请求也可能由 Codex 自动选择本技能。

## 主要能力

- 判断信息缺失是否会实质性改变结果。
- 将任务收拢为一句单点定义。
- 每轮询问 0–3 个价值最高的决策簇，没有最低数量。
- 说明每个问题希望确定的决策。
- 用户不知道如何回答时提供容易理解的选项。
- 先利用用户提供的文件、图片、链接和已有规格，避免重复询问。
- 每次回答后执行强制停止检查；不存在关键未知项时立即停止。
- 精确保留数字、范围、名称、指标、源字段等受保护约束。
- 仅在需要规划交付或跨智能体交接时生成可见的执行上下文。
- 访谈达到三轮时，额外生成人类可读的完整需求文档。

## 适用场景

当缺失信息可能实质改变方案类别、工作范围、执行路线、质量标准或验收条件时，应使用 Idea Refining。典型场景包括：

- 策划文章、故事、报告、产品或服务；
- 在偏好或硬约束不完整时进行产品推荐；
- 定义网站、应用程序或软件功能；
- 将早期想法整理成需求文档或可复用执行提示词；
- 收拢存在多个合理解释方向的请求。

它特别适合避免“结果看起来完整，但实际上解决错了问题”的情况。

## 不负责的内容

- 不对简单事实问题进行多余询问。
- 不强迫所有任务完成固定清单。
- 不设置通用的二次批准门槛；技能沿用原请求已有授权，受保护操作仍由宿主平台权限机制控制。
- 不对高风险领域结论提供专业正确性保证。
- 第一版不包含专业领域模块和脚本。

## 工作原理

技能按照以下循环工作：

1. 检查对话和用户提供的材料。
2. 将当前请求压缩成一句任务定义。
3. 识别真正会影响交付的信息缺口。
4. 删除重复、可推断、时机过早或可安全使用默认值的问题。
5. 每轮最多询问三个价值最高的决策簇，并更新任务边界。
6. 每次回答后重新检查；关键决策已经确认或能够安全、明确地采用假设时立即停止。
7. 根据执行意图，继续原任务、生成交接内容或输出不完整定义。
8. 交接前核对源事实，防止未确认的扩展被写成正式要求。

技能会展示近似完整度。完整度只表示需求是否被充分定义，不代表最终结论一定安全或正确。

### 决策簇

决策簇是一个能够选择或排除重要下游分支的自然选择。紧密关联、适合一次回答的信息可以放在同一个决策簇中，但不能为了减少编号而捆绑互相独立的问题。技术栈、数据模型、部署环境和视觉风格通常属于不同决策簇。

### 强制停止检查

每次回答后，技能都会更新已确认信息、假设、已作废答案和剩余关键未知项。当 `unknown-critical` 清零时立即停止。如果某个缺口可以使用不会实质改变结果的低风险假设处理，就应披露该假设，而不是继续追问。

### 执行路由

需求达到最小充分状态后，技能会在直接继续、可见交接和不完整定义之间选择。普通文本生成、只读分析、确定性转换以及原请求已经授权的实现工作可以直接继续，不增加技能层的二次批准。宿主平台的安全和权限控制仍然有效。

## 在 Codex 中安装

Codex 支持项目级和用户级技能。

只在一个项目中使用时，将整个目录复制到：

~~~text
<项目目录>/.agents/skills/idea-refining/
~~~

希望在个人的所有项目中使用时，复制到：

~~~text
$HOME/.agents/skills/idea-refining/
~~~

需要复制完整目录，包括 `SKILL.md`、`references/` 和 `agents/`。复制后，`SKILL.md` 必须位于 `idea-refining` 目录根部。

Codex 会从当前工作目录向项目根目录扫描 `.agents/skills`。用户级目录中的技能可用于本地多个项目。Codex 根据技能名称和描述发现技能，并在任务匹配时加载完整指令。

Codex 通常会自动发现新增或更新后的技能；如果技能没有出现，请重启 Codex。

当前安装和发现规则可参考 [Codex 官方技能文档](https://learn.chatgpt.com/docs/build-skills)。

## 使用方式

显式调用：

~~~text
$idea-refining 帮我定义一个用于点评学校及周边餐饮的网站。
~~~

~~~text
$idea-refining 我想写一篇文章，但还没有确定形式和重点。
~~~

技能已经允许隐式调用。当宽泛请求缺少会显著影响结果的决策时，Codex 可以自动选择本技能。

下面这样的简单请求不应触发技能：

~~~text
今天天气怎么样？
~~~

## 用户控制指令

用户可以说：

- **直接回答**：停止收敛，由宿主智能体继续处理原始任务，不增加技能层批准提示。
- **跳过**：暂时保留当前未知项。
- **使用推荐方案**：接受技能提出的默认选项。
- **返回修改**：替换之前的决定。
- **重新开始**：清空本次收敛状态并重新访谈。
- **先生成方案，不要执行**：只接收交接内容，不开始实际工作。

其他语言中的同义表达同样有效。

## 源信息保真

生成可见交接前，技能会将受保护事实与对话和用户材料逐项核对，包括数字、范围、单位、日期、名称、标识符、字段名、有序值、必须逐字保留的内容和统计含义。

技能不得把 `2–3` 个候选扩大为 `3–5` 个，不得把预算上限改写成目标价格，不得重命名源字段、擅自解释没有口径说明的百分比，也不得把推断扩展伪装成用户确认的要求。执行必需的源数据必须直接包含，或通过接收智能体确实可以访问的位置进行引用；否则应保留为未解决依赖，不能猜值。

## 输出方式

如果同一宿主智能体能够继续执行原请求已经授权的任务，技能会在内部使用收拢后的上下文直接继续，不增加仪式性的批准步骤。

如果用户要求规划交付或跨智能体交接，并且需求在一至两轮内达到可交付状态，技能会生成精简的智能体执行上下文。

如果访谈达到三轮，则生成：

1. 人类可读的完整需求文档；
2. 精简的智能体执行上下文。

如果达到最终续问上限时仍然缺少重要信息，技能会输出标记为“尚未具备可靠执行条件”的文档，并列出未解决的关键问题。

## 代表性评测示例

下面使用评测案例 SW-01，展示划定任务边界带来的实际提升。

用户最初只提出：

~~~text
帮我设计一个预约系统。
~~~

在没有收拢信息时，基线方案把它理解成面向诊所、培训、咨询或美容机构的客户预约平台，加入了客户、服务人员、排班、提醒、API、数据库和运营报表。方案虽然详细，却解决了错误的问题。

收拢过程确定了真正会改变结果的决策：

- **场景与用户：**约 70 人公司的内部会议室预约，使用者为普通员工和行政人员。
- **交付深度：**只需要产品需求及低保真页面和流程说明，不要代码或可点击原型。
- **核心目标：**避免会议室重叠预约，同时展示容量、设备和空闲情况。
- **角色权限：**员工可以预约并取消自己的预约；行政人员可以封锁维护时段并处理冲突预约。
- **范围边界：**使用公司邮箱登录；不包含参会人管理、外部日历、站外通知、支付、访客预约和会议室资料维护。
- **未定配置：**时间粒度、单次最长时长、可提前预约天数和临近开始后的取消限制保留为明确的待定配置，不擅自设置默认值。

最终收拢为：

~~~text
为约 70 人公司设计一套响应式内部会议室预约系统的产品需求及低保真页面和流程说明。员工使用公司邮箱登录，查看会议室容量、设备和空闲情况，创建预约并取消自己的预约；行政人员可以封锁维护时段，并取消与维护安排冲突的预约。系统必须防止同一会议室出现重叠预约，并清楚定义角色权限、冲突反馈和主要页面状态。本次不编写代码或可点击原型，也不加入参会人管理、外部日历、站外通知、支付、访客预约和会议室资料维护。未确定的预约限制统一标记为待定配置项。
~~~

收拢后的结果准确匹配了公司内部会议室场景，而基线方案已经进入无关的对外服务预约产品。这个提升来自少量能够改变结果的边界问题，而不是收集所有可能的产品细节。
